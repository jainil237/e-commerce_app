# Payment Integrity & Fraud Prevention — Plan

## Summary

Six phases, executed in dependency order on branch `payment-integrity`. The test harness lands first so every subsequent fix is proven by a test that fails before it and passes after. Fail-closed configuration (R2) lands second because it defines the single mock-mode switch that the confirmation service then consults. The shared confirmation service (R1 + R5) is the structural core: it collapses the two divergent confirmation paths into one, which is what makes the audit-log and coupon guarantees hold on both. Money correctness (R4) follows. The raw-body webhook change (R3) is sequenced **last and isolated**, because it is the only change that can take payment confirmation offline in production, and it is far safer to land it against a baseline that is already green.

Shipped as three stacked PRs: **PR-A** = Phases 1–2 (harness + config, no behaviour change to the happy path), **PR-B** = Phases 3–4 (confirmation service + money correctness), **PR-C** = Phase 5 (webhook raw body, isolated for independent rollback).

## Approach

Four decisions shape the implementation.

**1. One confirmation path, not two patched paths.** (carried from the brief's architecture decision) `POST /orders/verify-payment` and the `payment.captured` webhook both confirm payment, and today they disagree — the route increments coupon usage, the webhook does not, and neither writes an audit row. R1/R4/R5 are therefore implemented once, inside `payment-confirmation.service.ts`, and both entry points call it. The service owns the transaction boundary.

**2. Q3 decided — bind offline, verify amount by fetch.** Two-layer check:
- *Layer 1 (always, offline):* reject unless the submitted `razorpayOrderId` equals the order's stored `razorpayOrderId`. This alone closes the SEC-1 replay hole and costs nothing.
- *Layer 2 (non-mock only, network):* fetch the payment from Razorpay and require `status === 'captured'`, `order_id === order.razorpayOrderId`, and `amount === round(order.total * 100)`. This catches partial capture and out-of-band amount changes, which Layer 1 cannot see.
- *Failure handling:* if the fetch fails or mismatches, the request does **not** confirm the order. It returns a non-2xx and leaves the order `PENDING`. The webhook remains the authoritative confirmation backstop, so a transient Razorpay outage delays confirmation rather than losing the payment. Rejected alternative — compare only against the stored amount: simpler and offline, but blind to partial capture, and the amount it compares against is one we wrote ourselves, so it proves nothing an attacker could not also have influenced at order-creation time.

**3. Mock mode becomes one explicit switch.** `server/src/config/payments.ts` exports a single resolved boolean derived from an explicit `PAYMENTS_MOCK` opt-in, hard-disabled when `NODE_ENV=production`. The two existing inline `isMockMode` expressions (`order.routes.ts:265`, `rma.service.ts:326`) both consult it. Separately, `env.ts` asserts required payment variables at boot and exits non-zero in production when they are absent — a crashed deploy instead of one that accepts unsigned payments.

**4. Webhook change is isolated and last.** `express.json` is mounted globally at `index.ts:104`, before the webhook route at `:123`, so the raw mount must be inserted ahead of it and scoped to the Razorpay webhook path only. Getting that wrong breaks body parsing for the entire API, so it lands alone in PR-C against an already-green baseline, and the logistics webhook (signed differently, same router) keeps its JSON path.

## Dependency Order

```
P1 (harness)
 └─> P2 (fail-closed config)          — P2's assertions need P1's env-pinning setup
      └─> P3 (confirmation service)   — P3 consults P2's mock switch to decide whether to verify
           └─> P4 (money correctness) — P4's coupon atomicity lives inside P3's transaction
                └─> P5 (webhook raw)  — isolated last; lands against a green baseline
                     └─> P6 (verify + ship readiness)
```

Strict sequence, no parallelism. P3 before P4 is a hard dependency: R4's coupon-atomicity criterion is satisfied *by placing the increment inside the transaction P3 creates*. P5 last is a risk decision, not a technical dependency — it could run any time after P1, but it is the only change that can break payment confirmation in production, so it goes in alone and last.

## Architecture Notes

- **role:** Principal Engineer
- **decision:** Q3 resolved — two-layer amount verification (offline `razorpayOrderId` binding always; Razorpay payment fetch for status/amount in non-mock mode). Rejected stored-amount-only comparison: it validates our own written value and is blind to partial capture.
- **decision:** one `payment-confirmation.service.ts` consumed by both entry points, rather than parallel fixes. Follows the existing `rma.service.ts` transactional-service precedent; deliberately narrower than Epic 9's full domain-layer extraction.
- **decision:** P5 sequenced last and shipped alone. The user approved R3 without requiring last-place sequencing; this is my engineering call on RK1/RK7 grounds and can be resequenced on request.
