## Implementation Log

1. Cut `arb-remediation` from `main` per the plan. Migrations applied cleanly but produced no `OrderAuditLog`; investigation showed `main` has **no RMA subsystem at all** (no `rma.service.ts`, no RMA models, 3 migrations vs 4). The assessment was written against `feat/homepage-redesign`. Re-cut the branch from that tip, preserving work via `git stash -u`. `package-lock.json` conflicted on pop; resolved by restoring from HEAD and reinstalling. Raised as **B1**.
2. Built the harness. `setup.ts` must set `DATABASE_URL` before `src/` loads, because `src/config/env.ts` calls `dotenv.config()`, which does not overwrite already-set variables.
3. `migrate deploy` could not build a usable test schema — see **F1**. Switched the harness to `prisma db push`, then to drop-and-recreate per run after a leftover half-built schema hit a `DropTable` FK error.
4. Wrote characterization tests first (current behaviour, including defects), then the two security suites. Known-defect expectations are labelled with the finding ID and the phase that will change them; the three assertions that describe the *fixed* state use `it.fails`, so each flips to a plain `it` when its phase lands.
5. Eight tests failed with HTTP 429: `authLimiter` allows 5 requests per 15 minutes outside `NODE_ENV=development`, and its in-memory store is shared across the run (assessment TD-12). Replaced fixture logins with `authCookies()`, which mints the same JWT cookie `/auth/login` issues. Requests still exercise the real auth middleware; one test still logs in through the route.
6. One test then failed with HTTP 401 from `POST /orders`. Cause: the suite had set a real-looking `RAZORPAY_KEY_ID` for the whole describe block, so order creation left mock mode and called the live Razorpay API, which rejected the fake key. Narrowed the env override to wrap only the verify-payment call.
7. Full suite green: 26 passed, 4 files. Added CI and the compose file; typechecked.

## Findings Raised During Build

- **F1 — Migration drift; a database built from migrations alone is broken.** `CouponUsage` is in `schema.prisma` but no migration creates it, and migrations create `OrderItem` while the schema maps it to `orderitem`. A fresh environment (new developer, staging, DR restore) cannot run the coupon paths. Not in the assessment — it compounds the "no backup/DR strategy" risk (assessment R6). Worked around in the harness with `db push`; the fix is a generated reconciling migration. Suggest scheduling into Phase 4, which already has conditional schema approval.
- **F2 — `git stash list` holds `stash@{1}: On feat/homepage-redesign: playwright e2e lifecycle suite + config + dep`.** Prior end-to-end test work exists and was not incorporated. Left untouched. Worth reviewing before Phase 6 so the two suites do not duplicate each other.
- **F3 — `npm audit` reports 17 vulnerabilities (1 critical, 7 high)** across the pre-existing dependency tree. Pre-dates this chain; recorded, not acted on (assessment TD-11).

## Architecture Notes

- role: Senior Engineer
- decision: characterization tests assert today's behaviour, defects included, each labelled with its finding ID and owning phase. The three assertions describing the fixed state use `it.fails`, so the suite fails loudly if a defect disappears unexpectedly and each flips to `it` when its phase lands.
- decision: fixtures mint session cookies directly rather than calling `/auth/login`, to avoid the shared in-memory rate limiter. Auth middleware coverage is preserved; login itself keeps one dedicated test.
- decision: the test schema is dropped and rebuilt per run rather than migrated, because of F1. Guarded on a `_test` suffix so the command cannot reach a real schema.
- constraint: Build may not push, open PRs, or wait on CI, so the workflow file ships unexecuted.
- tradeoff: `db push` means the suite does not exercise the migration path. Accepted for now and recorded as F1; the comment in `global-setup.ts` names the switch back to `migrate deploy` once the missing migration exists.
- assumption for Review: `feat/homepage-redesign` is the correct base (B1). If the user prefers merging that branch into `main` first, Phase 1 rebases cleanly — nothing here depends on branch history.
- downstream: Phase 2 flips the SEC-1 `it.fails` to `it` and rewrites the SEC-2 test around the explicit `PAYMENTS_MOCK` flag; Phase 5 flips the TD-7 refund assertion; Phase 6 owns `npm run build`, `npm run lint`, and first CI execution.
